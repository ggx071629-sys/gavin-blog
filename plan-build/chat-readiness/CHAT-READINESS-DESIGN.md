# Chat 验证与运行恢复：设计依据

来源：本次对话的设计评估与云端运行说明；这是执行计划的引用基线，未实现或验证。
范围：现有真实问答入口的正常运行、重启与变更验证；不涉及云环境、部署或生产资格改造。

## D1 运行与重启校验

- 首次配置没有成功探测时，要求在明确预算内完成真实探测。
- 签名有效、配置匹配的成功记录，不因超过 24 小时而单独阻止正常运行、启动或重启。
- 记录年龄只作提示，显示最后验证时间；启动不自动发起付费 Chat 探测。
- 签名异常、配置不匹配、未来时间及无成功证据仍需明确拒绝，不伪装成普通过期。
- 保留现有 E5、索引、配置、readiness、输出校验、费用与熔断保护。
- 验收依据：运行跨过原到期点及旧记录重启均不要求付费复验；首次及无效证据仍受约束；无隐式付费；生产边界不被放宽。

## D2 复验与费用账本

- Key、endpoint、模型或输出协议变化，需要重新验证相关兼容性。
- 仅调整价格或预算，重新检查费用约束与授权范围，不因此调用模型。
- 保留原始验证事实与费用账本，不删除账本、清零费用或修改历史时间。
- 复验不能把有限次数的一次性验收账本误作无限日常额度；新增调用须有明确范围。
- 未结算/失败记录与额度耗尽需要可解释的恢复流程，不能无条件重试或重启清除熔断。
- 可记录最近正常调用成功时间，但不能据此冒充完整资格验证。
- 验收依据：触发条件可区分；费用及调用次数可追溯；失败和额度耗尽可按流程处理；无隐式付费。
- 待设计：探测兼容性与费用授权如何分别绑定、原账本如何保留并承接新授权、不同失败如何恢复。

## D4 取舍与实施边界

- 旧证据不证明供应商当前可用；行为变化可能由下一次真实问答暴露。
- 24 小时改成 7 天只推迟同一问题；启动自动探测会引入隐式付费，均不采用。
- 当前代码的年龄检查主要位于启动/签发路径，运行时 receipt 主要核对配置与签名绑定。
- 当前探测账本累计次数，并阻止带失败/未完成记录继续探测；恢复机制需单独设计。
- 本次只生成计划。后续行为变更按 Harness SDD/VDD 执行，不新增与本方案无关的验收门槛。
