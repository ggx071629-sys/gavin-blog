## 2. 实施前置与验证方式

未来启动时先读取当前阶段，核实代码版本、已有修改和对应问题；缺证据时定向复现。
用户可见行为及输入契约修改按 [SDD 规则](../../harness/specs/_sdd/README.md)建立短期 spec。
当前任务登记实际 `YYYYMMDD-short-slug` ID、文档影响及独立影响计划，实施前完成 spec-lint。
具体提交、检查及关闭遵循 [Specify](../../harness/workflows/specify.md) 与 [Verify](../../harness/workflows/verify.md)。
本轮规划不提前创建 active spec，不把 plan-build 历史归档当作 Harness spec 关闭。
沿实际源码归属和消费者选择精确检查；未知影响先补齐，不能按目录直接升级全量测试。
回归测试应能捕获原缺陷；自动检查与真实浏览器结果分别记录，不互相代替。
正常保存/发布使用真实后端，刷新或重进验证持久化，公开结果使用独立访客核对。
异常仅做明确受控注入，记录触发和撤销；不模拟成功响应证明业务完成。
桌面和移动检查沿用原审查的相关条件，移动为视口模拟，记录浏览器及实际尺寸。
复用 [原审查环境约束](../site-functional-audit/DESIGN.md#environment)；先确认隔离数据库、媒体、账号和端口。
旧服务已关闭；旧样本 ID、凭据和端口不是保证可用的前置，必要时重新生成专属样本。
新证据留 `.run/site-functional-fixes/<run-id>/`；提交仅含紧凑结果索引，不含截图、日志或秘密。

<a id="i004"></a>
## 3. I004：客户端首次加载错误

已确认：首页进入文章、关于进入读书时，列表请求 503 导致 URL 已变化但内容仍停留旧页。
修复目标：目标页面初次失败进入可理解、可恢复的错误状态，不能把旧页面呈现为新目标内容。
验收复用 C070：分别重现两个导航场景，确认错误反馈及操作内恢复入口；解除故障后恢复目标内容。
关联回归复用 C047/C069/C071：正常导航、搜索后续失败重试及关键词保持、真实缺失详情 404。
如更改共享错误处理，按实际调用关系补核其他受影响列表/详情，不预先宣称全部受影响。
不固定采用局部错误块或全局错误页；以页面语义、恢复结果及现有架构决定最小修复。

<a id="i003"></a>
## 4. I003：自动保存与临时标签输入

已确认：无关字段 PATCH 返回成功时，关于页尚未提交的新标签输入被清空。
修复目标：区分服务器保存结果与未提交的临时输入，避免无关保存静默删除正在输入的内容。
验收复用 C031：暂缓真实 PATCH、输入新标签、放行后输入仍保留；提交该标签后正常清理对应输入。
关联回归复用 C029/C030：领域与标签增删排序、现有限制、保存刷新、预览发布与草稿公开隔离。
排序和删除后的临时输入应仍属于正确领域；不为本缺陷扩大关于页业务或新增服务端字段。

<a id="i001"></a>
## 5. I001：读书封面地址一致性

已确认：媒体库返回相对媒体路径，封面字段要求完整 HTTP(S) URL，导致保存及发布受阻。
修复目标：媒体选择、表单校验和持久化读取采用兼容的地址约定，选中本站图片后可完成正常流程。
先核实已有前后端及媒体消费者契约，再选择地址规范化或兼容校验；不提前规定迁移方案。
验收复用 C024：从媒体库“使用 URL”选择封面，保存、刷新、预览、发布后访客实际显示同一图片。
关联回归复用 C023：既有合法 HTTP(S) 封面仍可保存，现有无效输入校验不失效。
不得以手填完整 URL 的替代操作作为媒体选择修复通过；不为兼容相对地址放宽到任意危险协议。

<a id="i002"></a>
## 6. I002：Markdown 换行兼容

已确认：同一 UTF-8 Markdown 内容使用 CRLF 时被报 front matter 缺失，LF 时成功。
修复目标：兼容这两种换行并保持现有元数据、正文、逐文件反馈及仅创建草稿的语义。
验收复用 C045：同内容 LF/CRLF 对照导入，三类受支持内容得到一致业务字段及正文内容。
关联回归复用 C043/C044：有效导入、重复 slug 拒绝、真实 ZIP 导出及其元数据正文。
原有缺失或非法 front matter 校验仍有效；不得通过宽泛吞错把不合法文件当作成功。
输入仍为 Markdown 文件，ZIP 仍是导出格式；不扩展新编码或其他导入格式。

<a id="o001"></a>
## 7. O001：标签提交偶发 pending

先在隔离环境关联浏览器请求、开发代理和 API 日志，核对请求是否到达及是否终止。
复查原重复 slug 场景及已通过的 409 反馈，区分产品缺陷、代理/环境问题与证据不足。
仅在根因和影响成立时提出针对性改动；涉及行为变化再按 §2 建立 spec 和回归检查。
未复现不是已修复；结论须保留尝试条件、事实、未知项及下一次需要的证据。
观察调查可以交付结论，但未知根因不得被标记为产品通过；尚未完成的处理或验证任务留在主计划。
不为消除观察记录而擅加全站超时、重试策略或永久遥测。

## 9. 进度与归档

状态：未开始＝尚未执行；进行中＝已启动；阻塞＝具体障碍阻止继续；未验证＝有操作但证据不足；完成＝该任务交付满足条件。
等待前置的任务保持未开始；本次规划全部 0 完成，不创建任何已完成任务记录。
执行时当前任务就地更新，主计划只保留有效范围、限制、阻塞及下一步，不逐轮追加日志。
任务完成后先将过程、关键决定、验证结果及证据索引写入 `completed/<阶段名>/<编号>.md`，再更新计数和下一任务。
未完成任务不归档；完成区只列完成状态与历史路径。阶段目录中的 `.gitkeep` 仅为空目录占位。
默认只读目标主计划，实施或验收再查上述相关章节，追溯具体事实才查任务历史。
