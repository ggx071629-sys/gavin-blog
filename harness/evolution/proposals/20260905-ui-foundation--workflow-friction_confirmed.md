## 问题与事实边界

闭环应判断“当前改动是否已有足够且可信的验证”，目前却把流程推进与重复执行整组门禁绑定。建议将计划、执行、运行记录和归档拆开。

静态代码核对得到以下事实，行号对应上述基线：

| 位置 | 当前行为 | 成本或后果 |
| --- | --- | --- |
| `harness/tools/harness.py:57–111` | 先执行全局 checks，但没有在其汇总失败后统一阻止产品 gate 启动；另有文档和合同等专门前置检查 | 部分已知治理错误仍可能伴随昂贵测试执行 |
| `harness/tools/product_verification.py:1157–1266` | 按 mappings 顺序执行，首个失败后停止；下次调用重新从首个 gate 开始 | 已通过的前序 gate 没有跨运行续用机制 |
| `harness/tools/harness.py:220–247` | close 默认调用完整 task verification，覆盖既有 evidence | 同一 HEAD 刚 verify 通过，close 仍再次执行 |
| `harness/tools/harness.py:284,322` | 关闭前后另有全局 checks | 包含治理和测试收集开销，不能全部称为业务全量测试 |
| `harness/tools/product_verification.py:445–475,1183–1192` | 已有包门禁满足子门禁下限的合同与运行证明 | 这是现有可保留能力；执行循环仍会执行同时显式列出的父、子 gate |

因此，“每次跑全仓库所有测试”并不准确；准确表述是“重试会重新执行任务声明的整组门禁，直到失败或全部完成；close 无条件再执行一轮”。`focused`、风险路由和包门禁证明已经存在，但没有解决跨运行复用。

另外，collector 已有同进程收集缓存（`harness/tools/test_collection.py:383`），不能把它误认成测试通过结果的缓存。E2E 入口先运行核心再运行助手（`apps/web/scripts/run-playwright-e2e.mjs:32`）；助手失败后重跑整个 e2e 会重复核心。普通质量构建与助手构建具有不同构建目录、开关和环境，不能仅因为都执行 build 就合并。

[最终关闭证据](../../verification/evidence/20260905-ui-foundation.json)记录四个 gate 耗时：Harness tests 41.5 秒、Harness integrity 20.8 秒、Web quality 266.1 秒、E2E 176.2 秒，合计约 504.6 秒（8.4 分钟）。这是最后一轮四个 gate 的记录耗时，不是整个任务总耗时，也不能据此推算所有重跑损失。

本次还有执行层面的责任：应先检查端口冲突和合同计数，避免把廉价可发现的问题留到长流程后段；在已知 close 自带验证后，不应再机械执行 verify → close 两轮。修复这些操作习惯仍不能替代失败续跑能力。

一次动态模块加载失败后原提交复跑通过，只能说明出现了间歇性失败；根因尚未证明，不能登记为已修复的环境问题。

## 目标与边界

- 流程步骤本身不使已经合格的测试结果失效。
- 每次执行都解释：需要哪些检查、为什么执行或复用、哪些结果失效。
- 失败、中断和环境错误保留可诊断现场；再次执行有明确起点。
- close 负责验证证据完整性和归档事务，缺少有效证据时报告缺口，不暗中启动长测试。
- 全量验证仍可由发布要求、风险规则或显式请求触发，不能由缓存绕过。

本草案只讨论仓库治理 Harness。第一阶段 UI 已关闭，后续 UI 阶段不在此次范围；不生成产品业务代码，不重写历史归档，不自动修改 `AGENTS.md`。初版不引入远端缓存服务、分布式调度或测试用例级依赖推导。

## 建议的职责划分

以下命令形态是拟议接口，当前尚不可执行：

| 操作 | 职责与结果 |
| --- | --- |
| `plan <task>` | 根据风险下限、AC 和当前输入生成执行计划；列出每个 gate 的执行/复用/失效理由，不启动产品测试 |
| `verify <task>` | 先预检，再执行缺失、失败或失效的 gate；保留每次 attempt；只有完整计划满足后才发布可关闭的聚合证据 |
| `status <task>` | 只读列出通过、失败、未执行、失效和可复用结果，给出下一条必要操作 |
| `close <task>` | 验证当前计划、运行凭据、AC 覆盖、清理结果和归档关系；原子归档，失败回滚 |
| `verify <task> --fresh` | 显式禁用结果复用，运行该任务所需的完整门禁集合；不同于完整产品 release |

完整 release 继续使用既有发布入口。是否允许某类 release 使用复用，必须由发布政策明确规定，初版保持其 fresh 执行要求。

计划中的 gate 集合与执行结果分离。父 gate 覆盖子 gate 时必须依赖现有规范命令合同和真实完成证明；不能仅凭名称省略子 gate，也不能把同一阶段在统计中重复计为新的验证。

全局检查也应按前置条件和关闭资产检查分组。close 保留必要的廉价一致性检查，不因为它们叫做“checks”就反复收集所有测试。哪些 checks 可去重，必须先分析输入和职责。

## 复用规则：从保守边界开始

初版只支持同一 task、同一 HEAD、同一规范计划与等价受控环境下的 gate 续跑。跨提交按路径判断是否失效放到后续阶段；仅凭 Git SHA 一致仍不足以允许复用，因为本地依赖和执行环境可能漂移。

每个 gate 的输入至少覆盖：规范命令和实际 npm script、测试选择与配置、锁文件和工具链身份、runner/collector 版本、执行平台与必要环境配置、测试数据初始化约定，以及依赖的构建产物。无法可靠识别的环境输入应导致不可复用，不采集或落盘密钥值。

后续跨提交复用使用显式、保守的 gate 输入范围，不先做复杂的测试级静态依赖分析。未知路径、公共合同、共享配置和 runner 改动默认扩大失效范围；单纯归档动作不应污染产品 gate 的输入身份。

成功结果复用不代表工作树和服务进程也复用。新运行仍建立隔离环境；旧产物缺失、摘要不符或前置构建已失效时，必须重建。拆分 Web quality 内的构建与测试，只有在产物可验证且依赖明确后才实施。

失败语义必须明确：

- 为每个 gate 保存独立 attempt；失败后的 gate 保持未执行，不能被统计为通过。
- 同一输入下出现新的失败，不得回退选用更早的通过记录来关闭；最新失败形成阻断，后续成功须保留其重试来源。
- 断言失败、启动失败、端口冲突、超时、收集失败和清理失败分别记录。端口冲突只报告归属，不能自动结束不属于本次运行的进程。
- 初版不自动无限重试。允许显式重试，但不把“后来通过”改写为“之前没有失败”；是否要求额外 fresh 验证由明确规则决定。
- gate 通过但隔离清理失败时，整次执行不能产生可关闭的凭据；保守作废相关运行的可复用状态。
- attempt 日志、trace 和截图在隔离清理前导出到本地受控目录；设置容量与保留策略，Git 只提交紧凑 manifest。

## 证据适用性与可信性

当前 [attestation 决策](../../docs/decisions/20260901-verification-attestation.md)把 close 全量重跑称为拒绝编辑 JSON 的必要成本。它确实避免直接接受被编辑的磁盘结果，但全量重跑不是唯一可选机制。不能删掉重跑后就把同一个可编辑 JSON 当作可信凭据。

需要分别回答三个问题：输入是否仍一致，记录是否来自被认可的 runner，以及全部必需检查是否确实完成。内容 hash 只解决前者和篡改检测的一部分，单独的自填 hash 不能证明执行来源。

建议保留当前“防误改和普通证据编辑，不防恶意同权限仓库写入者”的本地信任边界。候选实现是：runner 在仓库工作树之外维护本机运行记录与校验密钥，为完整 attempt 签发带认证码的凭据；仓库 manifest 仅引用凭据和摘要。close 校验来源、当前输入、失败历史、隔离清理和覆盖关系后生成归档。

该方案有明确代价：本机密钥管理、并发锁、原子写入、清理与跨机器不可直接复用。同权限恶意进程仍可能读取密钥，不能宣称这是外部不可变信任根。初版不承诺跨机器导入；凭据丢失或无法验证时重新执行受影响 gate。远端 CI 的可信结果需要另外绑定现有 CI 身份，不能随意导入本地记录。

落地前必须把凭据格式、认证算法与密钥位置、失败记录防回退规则、并发和崩溃恢复写入实施 spec。若评审认为本机持久凭据的维护成本不合适，可先只做前检和单次验证后直接关闭的流程收敛；这种替代方案消除相邻重复轮次，但不宣称解决了跨进程失败续跑。

## 实施顺序

| 阶段 | 交付范围 | 退出条件 |
| --- | --- | --- |
| A：先减少无效执行 | 前置失败立即停止；昂贵 gate 前检查依赖和端口；输出计划、阶段耗时与停止原因；保留失败产物 | 已知前置失败时产品 gate 调用数为 0；不再丢失首个失败现场 |
| B：同提交续跑与关闭分离 | 确定凭据信任模型；按 gate 保存 attempts；同 HEAD 续跑；close 消费有效聚合证据；保留归档回滚与历史摘要 | 同输入重试只执行失败/未执行 gate；verify 成功后 close 的产品 gate 调用数为 0 |
| C：按输入失效与内部拆分 | 有明确输入合同的 gate 跨提交复用；按需拆分 Web quality、构建产物与 E2E 阶段；保留 release 证明 | 无关改动不使已证明独立的 gate 失效；公共输入变更仍完整传播 |

优先完成 A、B 后用真实运行数据评估 C 的收益。维护复杂度、误复用风险和本地存储成本同样纳入比较，不以“缓存命中率越高越好”为目标。

实现需要新的 SDD spec；新的耐久决策放入 `harness/docs/decisions/` 并明确替代旧 attestation 决策的哪些条款。修改 config 或发布脚本可能触发现行 release 下限，不能为节省本次实施验证而临时降低现行门槛。

## 核心验收场景

1. A、B 通过，C 失败，D 未执行：输入相同时重试只执行 C、D；运行记录明确引用 A、B 的来源。
2. 同一输入下旧通过后又失败：close 被阻断，不能挑旧通过记录；重试通过仍保留失败历史。
3. verify 已全部通过：close 不调用构建、产品测试或全套 collector；验证归档关系后完成关闭。
4. 输入、规范脚本、测试配置、工具链或 runner 漂移：对应凭据失效并说明原因；未知依赖保守失效。
5. 修改 manifest、伪造退出码、删除必需凭据或破坏认证：关闭失败，且不产生半套关闭资产。
6. 端口占用、执行中断、隔离清理失败、并发 verify/close：不误报通过、不误杀其他进程；记录保留且可恢复。
7. 关闭时 HEAD/证据被并发修改：拒绝并回滚；归档、event 和 exact evidence digest 继续一致。
8. 显式 fresh 或要求 fresh 的 release：即使存在缓存也实际执行全部必需阶段，证明中区分执行与复用。

调度与证据规则优先使用可控的轻量 gate fixture 测试调用次数和状态转换，再用必要的真实 gate 验证隔离与产物交接。不要为了验证 Harness 的每个分支，分别启动一遍整站 E2E。
