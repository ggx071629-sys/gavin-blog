## 迁移前已核实的问题（历史背景）

- 迁移前，`harness/config.toml` 将 Web、API、Harness 目录变化分别映射到整个应用或整个 Harness 的 gate，没有模块级测试选择能力；某些脚本和配置还要求完整 release。
- 迁移前，全局 `module-coverage` 经 `module_verification` 调用跨 API、Vitest、Playwright 的 collector。收集不等于执行全部测试，但它仍消耗时间、进程和输出。
- 早期同 HEAD 重验复用了两个 gate；当时记录的前检约 24.1 秒、计划输入约 44.4 秒、输入复核约 47.2 秒，合计约 115.8 秒。该历史现场的本地备份为 `.run/impact/prior-resume-evidence.json`，不是当前主 evidence 的结果。产品测试调用减少，并不意味着端到端成本已经降低。
- 该轮 evidence 自报 passed，但实际 close 因缺少全复用场景的 isolation check 被拒绝；没有生成 archive/completion event。它不能作为“验证闭环已完成”的证明。
- 执行者在完整验证后继续补实现，产生多个新 HEAD 并反复全量验证，加重了原有问题。这是执行安排的责任，不能全部归因于工具。

## 核心原则

唯一的测试范围依据是改动后的实际影响。先分析变更、模块契约和依赖，得到受影响模块集合，再选择这些模块的测试；不能把修改文件所属模块、顶层目录或整个项目直接当成测试范围。

1. 每项变更先确定受影响模块集合及其对应 cases/test refs，只执行该集合内的相关测试。修改位置是分析输入，不能直接替代影响判断。
2. 依赖模块只有确实受到本次改动影响才进入集合；仅仅存在依赖关系不足以扩大范围。公共契约、数据流或共享实现的影响传播必须逐项说明。
3. 未识别文件、缺失归属或依赖关系不完整时，阻断并报告具体缺口；禁止静默提升到整个项目测试作为兜底。
4. 当前模块改动任务只有在实际影响覆盖全项目时，测试集合才可能覆盖全项目。另行明确请求的发布验证是独立任务，不能以发布政策为由扩大普通改动的测试范围。不能只因文件位于 scripts/config 就默认认为它影响整个产品。
5. 缓存是可选优化，不能成为每个普通任务的强制前置成本。决定是否复用时必须比较检查成本和所选测试成本。

## 预期选择行为

| 变更输入 | 影响分析后的选择 | 纳入依赖模块的条件 |
| --- | --- | --- |
| 某个功能模块的实现 | 受影响模块对应的 unit/integration/case tests | 其输出契约或共享数据确实影响其他模块时加入对应依赖测试 |
| 某个页面或组件 | 所属功能模块的组件测试与相关 E2E 场景 | 共享组件 API 或跨模块交互变化时加入相关使用方 |
| 某个 API 模块 | 该模块接口、领域行为及合同测试 | 接口合同改变时加入实际调用方的合同/集成测试 |
| 某个 Harness 工具模块 | 该工具的测试及受影响治理合同 | 例如认证记录改变影响 close，则加入 close/history 相关测试；不因此运行 Web/API 测试 |
| 文档、索引 | 相关 metadata、links、index 检查 | 文档声明改变了可执行合同，才加入该合同的验证 |
| 共享合同或配置 | 读取该合同/配置的模块集合 | 只有依赖影响覆盖全项目时才提升为全项目 |

## 实施方向

### 模块和测试选择成为主流程

复用现有稳定模块 ID、case 和 exact test refs，补齐必要的源码归属与模块依赖。规则优先保守、显式、可审查，不先建设复杂静态依赖推导系统。产品模块内部也需支持更细的工具/组件归属，避免用 M08 这样的宽泛模块名继续包住全部 Harness 测试。

计划独立保存：改动文件、所属模块、受影响依赖、选中/排除的测试及理由。规范 runner 根据该计划构造受限 Pytest 路径/node ID、Vitest 文件/test name 和 Playwright spec/project 选择器；不能把任意 shell 放进 spec，也不能只加筛选参数却仍在脚本内部执行完整套件。

拆分现在混合在一起的两类操作：全仓合同的廉价结构检查，与所选模块 exact refs 的真实收集。普通任务只收集选中的模块；全仓 collector 放在 collector/合同机制本身受到广泛影响的集成验证节点，或明确发布节点。

### 减少重复验证和输出

本地实现过程中使用所选模块的针对性验证；集中完成实现与审查后，再进行一次必要的最终验证。收尾沿用这次 runner 的真实结果，不能因为 commit、verify、close 的命令步骤机械增加一轮相同测试。

优先评估“受影响模块的所选检查运行一次后同进程归档”的低成本收尾路径，保留来源和覆盖校验。跨进程缓存只对足够昂贵、输入合同清晰的 gate 启用；不得为了复用几秒的模块测试，扫描整套 node_modules/.venv 数十秒。不能通过取消真实性检查或接受手写 passed JSON 来降低开销。

成功输出只保留范围、结果、耗时与下一步的紧凑摘要；失败给出首个相关诊断和本地日志位置。收集数量、实际执行数量、复用数量分别记录。若无法直接测量模型 token，就报告输出字符数/字节数作为代理指标，不虚报 token 数。

### 迁移既有门槛

现行 `risk_routes` 的固定全量 gate 下限必须由明确的模块影响规则替代，不能在任务 spec 中偷偷绕过。release 是否全量继续由明确发布政策规定，普通模块修改不自动等同发布。先用轻量 fixture 验证选择规则和调用次数，再对一项 Harness 模块变更与一项产品模块变更做必要的真实验收，不为每个分支启动完整 E2E。

### 验证闭环与失败处理（吸收旧提案）

plan/status 只读地解释选择范围、执行与复用计划、失效原因，不启动产品测试。执行前只检查相关的廉价前置条件；条件失败时阻止依赖它的昂贵检查。verify 按所选范围执行，必需检查齐备才发布 passed 聚合证据。`--fresh` 仅强制重新执行本次受影响范围内的必需检查，不表示全项目测试。

每次尝试独立记录；失败后尚未执行的检查保持 not-run。同输入下的新失败阻止使用旧成功绕过失败；重试只执行仍缺少有效结果的所选检查，保留失败历史和复用来源。区分断言、启动、端口、超时、收集及清理失败，不无限自动重试，也不把随后通过当作间歇故障根因已修复。端口冲突报告占用者，不终止其他任务的进程；清理失败阻止该次结果复用及任务关闭。

在销毁隔离环境前，导出排障所需的有界日志、trace 或截图；本地产物设置保留期和容量限制，Git 仅保存紧凑 evidence manifest。

### 证据、隔离与关闭事务（吸收旧提案）

证据分别证明当前输入适用性、真实 runner 来源和必需检查完整性。可编辑的 passed JSON 或自行填写的 hash 不构成执行证明。输入合同覆盖所选检查实际依赖的命令、脚本、配置、工具链、初始化及产物；只核对相关输入，不默认扫描整个安装依赖目录。无法证明适用性时不复用相应结果；影响关系缺失时报告缺口，不扩大到全项目测试。真实性机制明确同用户本地信任边界，不声称能防御拥有同等权限的恶意操作者。

复用测试成功不等于复用服务或构建产物；所选检查需要的产物缺失或不匹配时，只重建相关依赖，不能把不同构建目录、开关或环境的构建直接合并。父 gate 只有具备规范命令合同及真实完成阶段证明时才能覆盖子 gate，避免重复执行和计数；不能为了取得父 gate 证明额外运行无关模块。

close 消费足够且可信的证据，核对验收覆盖、隔离清理和归档关系；证据缺失就报告具体缺口，不暗中重跑测试、构建或 collector。关闭期间源码、计划或证据变化时拒绝并回滚，保证 archive、completion event 和 exact evidence digest 一致。并发互斥、中断恢复与原子归档不得留下半套关闭资产，失败记录仍可追踪。

### 合并边界与既有实现

不再继承旧提案“先完成 A/B 同 HEAD 缓存，再考虑范围拆分”的实施顺序。先落实受影响模块选择，再按真实收益决定是否保留跨进程缓存。HMAC、密钥位置、独立本地账本不是本提案指定的必选架构；同进程可信收尾与可选持久化证明应按成本比较。全依赖指纹扫描、未知路径全项目兜底、scripts/config 变更自动触发完整 release 均不能作为普通任务默认路径。

已有 A/B 提交逐项按范围正确性、闭环可用性和端到端成本重新评估，不因已经实现就全部沿用。终结旧提案本身不表示 A/B 已验收，也不触发当时 active 的 `20260905-harness-resume` spec 关闭；该 spec 后续的实际归档及其验收边界见下文。既有事件和运行记录继续保留。

## 必须通过的验收

- 测试范围等于有依据的受影响模块集合；未受影响的模块不收集、不构建、不执行，无论改动行数或文件位于哪个目录。
- 公共契约变更仅扩展到有依据的依赖模块；计划说明每个新增检查的原因。
- 未知归属会报告缺口，不自动执行全项目。
- 文档检查产品测试调用数为 0，跨项目 collector 调用数为 0，整套安装依赖扫描次数为 0。
- 多次本地修改不会形成 verify → commit → verify → close → verify 的固定循环；最终测试来源和实际检查范围可追踪。
- runner 不得发布 close 无法消费的 passed 聚合证据；全复用、部分复用、清理失败和中断均有真实 CLI 闭环测试。
- plan/status 与 close 的产品测试、构建和 collector 调用数为 0；fresh 仍只执行受影响范围，相关前置失败不会启动依赖它的昂贵检查。
- 用轻量 fixture 覆盖失败后未执行、旧成功后新失败、凭据篡改、输入失效、父子 gate 去重及产物缺失；补充必要的所选模块 CLI 场景验证隔离清理、并发和归档回滚，不为每个分支运行整站 E2E。
- 在同一受控环境下，对模块任务比较修改前后的端到端时间、执行范围和输出量。调用次数减少但总成本增加，不能判定为优化成功。
